## 3. Non-reflowing layout and the actual per-frame update cost — the key finding of this pass

The brief's own framing ("every frame a system rebuilds a multi-thousand-character `String` and assigns it into that `Text`") is exactly the failure pattern Bevy's own text-change-detection system is built to warn you off, and I found the mechanism directly in the vendored source rather than inferring it — this is new, not in the original 108-agent harvest.

**[synth-verified, vendored source]** `bevy_text-0.18.1/src/text.rs:744` — `detect_text_needs_rerender<Root>` runs every frame and sets `ComputedTextBlock.needs_rerender = true` whenever `Changed<Root>` fires (`Root` = `Text` for UI, `Text2d` for world-space) — i.e. **any** write to the `Text` component's string, regardless of whether the visible content actually differs, marks the whole block dirty. The struct field's own doc comment (`text.rs:60-67`) is unusually candid about what that costs:

> "This field currently causes UI to 'remeasure' text, even if the actual changes are non-structural and can be handled by only rerendering and not remeasuring. A full solution would probably require splitting `TextLayout` and `TextFont` into structural/non-structural components for more granular change detection. A cost/benefit analysis is needed."

So the engine's own authors flag this as unresolved: **a per-frame `String` reassignment into one big `Text` forces a full Taffy remeasure + relayout every frame**, not just a re-rasterize — this is the actual mechanism behind the defect the brief diagnosed, not merely a symptom of the string being "multi-thousand-character." A one-character digit change would trigger the identical remeasure cost.

This corroborates and *sharpens* two harvest claims that were only tangential/unverified on their own:
- Bevy issue #15805 (harvest, unverified) — "change detection for text is more painful after text rework," filed by Bevy's own lead maintainer, open since 2024-10-09, still open as of 2026-07-31 fetch. That issue is scoped to *ergonomics* of detecting a change from the outside, and explicitly disclaims making any layout-cost claim — my source read above is what actually substantiates the layout-cost side.
- `iyes_perf_ui` (harvest, unverified but corroborating in spirit): its own perf notes say a full debug overlay's frame cost is "most of which is CPU time spent in Bevy's UI layout systems (in `PostUpdate`)" — independent evidence (different codebase, different era) that Taffy layout, not text rasterization, is where a naive per-frame HUD pays.

**Design consequence, stated plainly:** the fix is structural, not a settings knob. Split the volatile numeric/status values out of the single giant `Text` into their own small `Text`/`TextSpan` entities, one per chip-value, and only write to each when its value actually changed (gate your own system with a comparison, or Bevy's `DetectChangesMut::set_if_neq`, so writing the same value twice doesn't re-trip `Changed<Text>`). Most frames then touch zero text entities. Combine with:
- **[harvest-verified, SURVIVED 0R/3K]** a small, fixed type scale (a handful of discrete font sizes) — a distinct font atlas is generated per `(font handle, scaled font size)` pair with "a strong performance impact" per the docs.rs 0.18.0 warning, so a per-chip size ladder or continuously-animated font size is a real, avoidable cost, not a free effect.
- **[harvest, unverified but consistent]** fixed-width digit slots for numeric readouts (reserved-width nodes, not auto-sized-to-content) — bevy issue #15197 (closed, fixed in 0.15 for the rounding-jitter *bug*, but the issue's own diagnosis of the *destabilizing pattern* stands independent of that fix): auto-sized or right-aligned nodes whose measured width changes frame-to-frame because digit count changes are the specific construct that produces visible 1px jitter, and the effect "scales with `scale_factor`... invisible at scale factor 1" — meaning this class of bug is invisible in a 1x dev session and only shows up at Retina capture scale, exactly the capture path this project cares about.

## 4. Attention affordances (pulsing/blinking without a hand-rolled per-chip timer)

This is where the harvest's most confidently-stated capability claim **fails on its operative half** — worth landing carefully since it changes the recommended crate.

**[harvest-verified, REFUTED 3R/0K]** The original claim: "Bevy 0.18 introduces a `TryStableInterpolate` trait that makes `Color` and `Val` animatable... i.e. pulsing/fading alert chrome ... [has] first-party support rather than requiring a hand-rolled per-element timer." The trait's existence and its three implementors (`Color`, `Val`, presumably a third) are true. The "i.e." conclusion is false: three separate verifier passes independently confirmed `TryStableInterpolate::try_interpolate_stable(&self, other, t)` takes `t` **as a caller-supplied parameter** — nothing drives it. Bevy's actual animation-clip/`AnimationPlayer` machinery (`bevy::animation::animation_curves`) binds to the *different* `Animatable` trait, whose implementor list does **not** include `Color` or `Val` at 0.18. So `TryStableInterpolate` is a safe, unit-mismatch-aware **lerp helper you call from your own system that already has a `t`** — it removes footgun math, not the system itself. There is no first-party "attach this component, it blinks" primitive in 0.18.

Given that, the ecosystem answer earns its keep here:

**[harvest-verified via corpus, crate itself unverified independently in this pass]** `bevy_easings` — actively maintained, released versions tracking Bevy releases directly (0.18.0 published 2026-01-25, 0.19.0 published 2026-06-24, crate alive since 2020). It implements `Lerp` for `Node`, `BackgroundColor`, `TextColor`, `Val`, `UiRect` (behind a `ui` feature; `BackgroundColor` additionally needs `render`), and its `EasingType` enum ships `Loop { duration, pause }` and `PingPong { duration, pause }` as **data fields on the component**, which is exactly the "no hand-rolled per-element timer" shape — the crate's own system does the driving, you just declare the waveform. For a hard on/off alarm blink rather than a sinusoidal fade, `EaseMethod::Discrete` ("value jumps from start to end") is the documented primitive for that.

Two caveats worth carrying forward, both from the harvest and neither independently re-checked here:
- Easing a `Val` across mismatched unit variants (`Px` ↔ `Percent`, or anything touching `Val::Auto`) **silently no-ops** — falls through to a catch-all returning the unchanged start value, no panic or warning. An alarm chip whose position/size animation "just doesn't move" should make you suspect a `Val` unit mismatch first.
- `bevy_easings`' confirmed `Lerp` impls do **not** include `UiTransform` (the layout-free scale/rotation type from §3's table) — only `Node`/`BackgroundColor`/`TextColor`/`Val`/`UiRect`. If the design wants a scale-pulse rather than a color/alpha pulse, that path is unconfirmed by the corpus and worth a five-minute check against the crate source before relying on it (it wasn't checked in this synthesis pass either — flagging as open, not as refuted).

## 5. Crisp small text over busy 3D imagery — contrast, hinting, smoothing

This cluster had the highest concentration of harvest claims that flip on verification. Landing them correctly matters because it's the brief's stated top priority.

**Font hinting — the claim's polarity was backwards.** **[harvest-verified, REFUTED 3R/0K]** The original harvest claim (from PR #22308's body) said UI `Text` requires `FontHinting::Enabled` and `Text2d` requires `Disabled`. Verified directly against the shipped `v0.18.0` and `v0.18.1` tags: it's the **opposite** — `Text` requires `FontHinting::Disabled`, and so does `Text2d`. A follow-up PR (#22494, "Disable font hinting for UI text by default," merged 2026-01-13 — the same day 0.18.0 was tagged) flipped the UI default before release. **Practical read: hinting is off by default for both UI and world-space text in shipped 0.18/0.18.1.** If the panel wants hinting on, it must be set explicitly per text-block entity (not per-span — confirmed harvest claim, SURVIVED, hinting was deliberately kept off `TextFont` because it's a block-level not span-level concept).

**Font smoothing is NOT a no-op — the harvest's own "limitation" claim was itself a version-attribution error.** **[harvest-verified, REFUTED 3R/0K, and independently re-checked by me this session — synth-verified]** The harvest pulled PR #22455 ("`font_smoothing` field of `TextFont` is ignored in main currently... milestoned for 0.19") and concluded 0.18 ships a dead knob. Wrong on two counts: (1) the PR's "main" was already deep in the 0.19-dev cycle by the time it was opened (2026-01-09), four days *before* 0.18.0 was tagged from a separate release branch; (2) I read `bevy_text-0.18.1/src/pipeline.rs` directly this session (not just the harvest's vote citations) — `font_smoothing` is read per-glyph at line 399 (`let font_smoothing = self.glyph_info[span_index].1;`) and at line 401 gates real behavior: `if font_smoothing == FontSmoothing::None { ... round the glyph positions and sizes, effectively discarding all subpixel layout ... }`. That is the field being consumed, not ignored — the hardcoded-`AntiAliased`-override bug PR #22455 describes and fixes is simply absent from this file at 0.18.1. **`FontSmoothing::None` works in shipped 0.18.** It's a real, per-text-entity, functioning lever (specifically: it snaps glyph position/size/offset to integer pixels rather than leaving subpixel placement, which is itself directly relevant to "crisp small text" — worth surfacing as its own finding, since the harvest's claim pool described `FontSmoothing` only as an antialiasing toggle and missed that its `None` variant is also a pixel-snapping mechanism).

**What smoothing actually offers — contested claim, majority-survived.** **[harvest-verified, contested 1R/2K, majority keep]** Exactly two modes exist: `AntiAliased` (default grayscale) and `None` (pixel-art, no AA) — the enum shape itself was not in dispute even in the dissenting vote ("the narrow `FontSmoothing` fact is verbatim-accurate"). The recorded disagreement was over the claim's closing framing — "crispness must be bought... rather than through a rendering mode" — with the dissent stating that conclusion is "contradicted by the same crate at the same version"; the transcript is truncated before it states exactly what contradicts it, so I can't tell you the dissent's specific citation. My own finding just above is a plausible candidate for what it's pointing at: `FontSmoothing::None` doesn't just toggle antialiasing, it also pixel-snaps glyph geometry, which is arguably "crispness... through a rendering mode" after all — but that's my inference connecting the two, not something I can attribute to the dissenting vote with confidence. Either way, the practical takeaway holds: the binary on/off (now known to include pixel-snapping when `None`) is the entire smoothing lever; the rest of legibility comes from contrast affordances (below), integer/physical-pixel-aligned sizing, and font choice.

**Contrast affordances that DO exist first-party, all confirmed against the `bevy_ui`/`bevy_text` 0.18.0 API surface (harvest-verified, SURVIVED 0R/3K unless noted):**
- `bevy_ui::widget::TextShadow` — `offset: Vec2` (logical px) + `color: Color`. Implemented as glyphs redrawn at an offset (not a blurred shadow; blur was explicitly deferred as needing shader work) — roughly 2× text draw cost, per the original PR author. UI-only.
- `bevy_sprite::Text2dShadow` — the `Text2d` (world-space) equivalent. **This directly overturns another harvested claim** that "`Text2d` gets no first-party shadow" — that claim was true of Bevy 0.15/0.16 and false by 0.18 (`Text2dShadow` landed via PR #20463, merged 2025-08-14, present at the `v0.18.0` tag). If either the earlier "no Text2d shadow" sentence or this correction gets carried into the dossier, carry the correction.
- `TextBackgroundColor` — per-span background, lives in `bevy_text` itself (so reachable from both UI and `Text2d` contexts without the UI crate).
- `Outline` and `BoxShadow` (with `blur_radius`) on `bevy_ui::Node` for chip-level (not glyph-level) chrome — `Outline` is explicitly documented as layout-free ("do not take up space in the layout"), so a focus/alarm ring can appear/disappear without shifting sibling chips. Same evidence that backs §1's "scale/rotate without reflow" row.
- **What's genuinely NOT available:** a real glyph-edge outline/stroke. Issue #17076 (opened 2025-01-01) is still open, but — correcting the harvest's own claim about it — **it is not orphaned**: `gh api .../issues/17076/timeline` shows real cross-referenced work, including an open PR **#23369** ("feat(text): add coverage-based text outlines," `S-Needs-Review`, last updated 2026-05-05). So "no native outline" is accurate for 0.18 today, but "abandoned, no work in flight" is not — there is a live PR that could land in a future release. Track it if outline-for-contrast becomes a hard requirement rather than a nice-to-have; today's answer is still hand-rolled (duplicate offset copies, "sometimes 4 shadows... to create a fake border," per a maintainer comment) or `Text2dShadow`/`TextShadow` alone.
- Tabular/lining numerals: `TextFont::font_features: FontFeatures`, with `FontFeatureTag::TABULAR_FIGURES` / `OLDSTYLE_FIGURES` / `STANDARD_LIGATURES` reachable via `FontFeatures::builder()` — confirmed reachable from the public component API, no custom pipeline needed. **Caveat not previously flagged in the harvest:** this only works for `.otf` fonts that carry the feature tables; the `default_font` Bevy ships (described, by a community source in the `bevy_screen_diagnostics` README — not a primary Bevy source, so treat this specific fact as a lead rather than confirmed — as "a stripped version of FiraCode") is not guaranteed to. If numeric-column stability via `tnum` is wanted, budget for shipping a real `.otf` and loading it via `AssetServer`, not relying on the built-in default font.

**DPI / Retina.** `TextFont::font_size` is a logical-pixel quantity multiplied by window scale factor × `UiScale` to reach physical rasterization height — **not** by the entity transform or camera projection — so UI text is auto-crisp at Retina with zero manual DPI code. One nuance surfaced only in a verifier's own citation trail, worth carrying forward even though it wasn't itself a submitted claim: `UiScale`'s doc comment says it "will only affect fixed ui values like `Val::Px`" — i.e. percentage-based sizing is not rescaled by the global `UiScale` lever, only literal-pixel values are. If the panel wants one global "make everything bigger" knob, size things in `Val::Px` deliberately, not percentages, or `UiScale` won't reach them.

The asymmetric-DPI finding for **images**, not text, remains live and unresolved: bevy_ui text is re-rendered crisp at physical resolution automatically, but UI *images* are naively upscaled and blur — a 2023-11-14 issue, still open, no milestone, ~2.7 years untouched. If any panel chrome uses raster icon assets (not glyphs/vector) rather than text glyphs for state (e.g. an alarm icon), that's the one area DPI-crispness is genuinely unsolved by the engine and would need hand-authored @2x-style asset variants plus a manual system to pick them — there is no first-party mechanism.

## 6. World-space anchoring and the off-screen indicator

**[synth-verified, vendored source]** The harvest's issue #20590 claim ("`Camera::world_to_viewport` returns render-target-relative, not viewport-relative, coordinates when the camera's viewport has a non-zero origin") was in the sources pool but never entered the 25-claim vote. I checked it directly against `bevy_camera-0.18.1/src/camera.rs:501-531` (`world_to_viewport_core`): the last line of the function is

```rust
let viewport_position =
    (ndc_space_coords.truncate() + Vec2::ONE) / 2.0 * target_rect.size() + target_rect.min;
```

`target_rect.min` is unconditionally added — confirming the claim is **still true at 0.18.1**, not just at the 0.16 the issue was originally filed against, and confirming the corollary the harvest drew: for a full-window camera (viewport origin `(0,0)`), the bug is inert and `world_to_viewport` behaves as expected; only a camera with a non-default viewport rect (split-screen, inset minimap, etc.) needs the manual `- target_rect.min` correction. If `vivarium-explore`'s main 3D camera is full-window (as the brief's description of a single rotating globe suggests), this is very likely a non-issue in practice — but worth a one-line comment at the call site either way, since the failure mode if the camera setup ever changes is silent (wrong screen position, not a panic).

**Anchoring a UI node to a world point — the crate to use, and the version trap.** `bevy_ui_anchor` does exactly this: `AnchorUiNode` continuously drives a UI node's screen position from a world position or another entity's `GlobalTransform`, with `AnchorPoint`/`HorizontalAnchor`/`VerticalAnchor` selecting which corner of the UI node pins to that point. **The version trap the harvest caught:** the crate's *latest* release, 0.12.0 (2026-07-08), requires `bevy ^0.19.0` and will not compile against 0.18 — the correct pin for this project is **0.11.0** (2026-02-15, `bevy ^0.18.0`), confirmed three independent ways (crates.io dependency API for both versions, docs.rs for 0.12.0). The crate is otherwise a good sign: 21 releases since 2024-08-07 with no yanks, one release per Bevy cycle through 0.14→0.19, so it hasn't fallen behind the way most of the ecosystem-crate pool has (contrast with §9's table). Two real caveats: it requires tagging your camera with a marker component (`UiCameraMarker`) or it silently anchors nothing; and documentation coverage is thin (38.89% per docs.rs), so budget time reading its ~2000-line source rather than its docs page.

**Off-screen indicator — genuinely not a solved problem in the corpus.** Neither the crate's docs nor its README (as fetched) document any clamp-to-edge or arrow/bearing behavior — the harvest explicitly flags this as unconfirmed rather than asserting it's absent, which is the right epistemic posture and I did not attempt to re-derive it from source (out of scope for the vendored-crate check, since it's not a locally-vendored crate). Treat "off-screen indicator" as **hand-rolled on top of** either `bevy_ui_anchor` or raw `Camera::world_to_viewport`: project the point, and when it falls outside the viewport rect (or behind the camera — `world_to_viewport` returns `Err(PastNearPlane)`/`Err(PastFarPlane)` for that case per the source read above, which is itself a useful built-in signal for "this target is off-screen" separate from merely being outside the rect), clamp the projected position to the viewport edge and rotate an arrow glyph/icon by the `atan2` bearing from screen-center to the (unclamped) projected point. This is standard, well-understood work — just not something Bevy or its ecosystem hands you pre-built.

## 7. The screenshot path

**[synth-verified, vendored source]** `bevy_render-0.18.1/src/view/window/screenshot.rs` confirms the mechanism `vivarium-explore`'s own `main.rs`/`capture.rs` already use: spawn a `Screenshot` component (`Screenshot::primary_window()`), `.observe(save_to_disk(path))`, and Bevy fires a `ScreenshotCaptured` event with the image once ready. This is exactly the pattern at `main.rs:1627` and `:1749` in this repo today — **the current implementation is on the documented, current, first-party path**, not something ad hoc. Good news, worth stating plainly rather than treating as a research gap.

**The one real landmine, and it is not about `bevy_ui` — it is about anything that draws *outside* Bevy's render graph.** The screenshot mechanism works by redirecting the render target away from the swapchain to a copyable texture (documented in Bevy's own source comment on `ExtractedWindow::swap_chain_texture_view`, quoted directly by a `bevy_egui` maintainer). `bevy_ui` renders through Bevy's normal render graph, so it is captured correctly by construction — this is implicit in the mechanism, not a separate claim needing its own check. But `bevy_egui` (pre-0.35) draws straight to the window's swapchain texture, bypassing that redirect entirely, so **its UI was silently absent from every committed screenshot** — a real, filed, `P-Regression`-labeled Bevy issue (#16689, reported against 0.15, only ever fixed on the egui side in 0.35, no app-level system-ordering workaround exists per the reporter's own exhausted attempts). Given §1's pinned-version fact that a Bevy-0.18-compatible `bevy_egui` is frozen at 0.39.1 (2026-02-06) — **update 2026-07-31:** `bevy_egui` 0.39.1's own crates.io dependency manifest requires `egui ^0.33`, which cannot resolve to 0.35 absent an unconfirmed backport; two external audits split on whether that closes the question (one flips the default assumption to hazard-present, one calls it still correctly open — see `03-implementation-concerns.md` §7 for both positions stated in full) — the safer, already-verified-safe path is simply not to introduce an immediate-mode UI layer into a project whose defining requirement is "captures committed to the repo as evidence." This is a second, independent line of argument (beyond Feathers' own "not for product UI" disclaimer in §8 and beyond the version-lag detailed in §9's ledger) against reaching for `bevy_egui` here, and it's the one most specific to this project's screenshot-as-evidence requirement.

One more finding from the same defect thread, worth keeping as a general caution about screenshot-based verification itself rather than about this panel specifically: Bevy's own screenshot-based CI failed to catch the `FontSmoothing` no-op-on-`main` regression discussed in §5 before it shipped to `main` (the PR that fixed it names this as one of its own stated objectives) — i.e., a passing screenshot-diff CI is evidence of *gross* visual regressions, not of subtle rendering-mode defects. Don't over-trust "the screenshot looked the same" as proof that a rendering-flag change actually did anything.

## 8. First-party widget layers — Feathers and `bevy_ui_widgets`

Both are real, both are shipping in 0.18 (not aspirational), and both are the wrong layer for most of this panel — but not for the reason "experimental" alone implies, and there's one genuine find inside `bevy_ui_widgets` worth adopting.

- **Neither ships enabled by default.** `experimental_bevy_ui_widgets` and `experimental_bevy_feathers` are both non-default Cargo features at 0.18.1 (confirmed via the docs.rs features tab); `vivarium-explore`'s current `bevy = "0.18"` with no feature list gets neither. `experimental_bevy_feathers` transitively pulls in `experimental_bevy_ui_widgets` (styling sits atop behavior, not beside it).
- **Feathers (the styled layer) explicitly disclaims product use, from three independent primary sources that all say the same thing** — its own 0.18.0 and 0.18.1 crate docs ("it's deliberately not intended for that... consider copying this code into your own project"), and the 0.17 release notes calling it "Bevy's developer tools... utilitarian look and feel... tailored for editors." Convergent, not merely repeated: three separately-fetched primary documents at different points in the release history all land on the identical verdict. Its inventory is form controls only (button/checkbox/radio/slider/color-picker/toggle/virtual-keyboard) — nothing chip/panel/banner/toast-shaped exists in it regardless of the "don't use it" advice.
- **`bevy_ui_widgets` (the unstyled behavior layer) is a reasonable pattern reference even though it isn't a widget match either** — its inventory is also form-controls-only (Button/Checkbox/RadioButton/RadioGroup/Slider/Scrollbar/MenuButton/MenuItem/MenuPopup), external-state-management by default (widgets emit `Activate`/`ValueChange<T>` events rather than self-mutating), which is architecturally the right shape for a HUD driven by simulation state rather than user input — but there's still no status-readout primitive in it to adopt directly.
- **The one genuine surprise, not in the original 108-agent harvest at all — found by reading the source directly during this synthesis:** `bevy_ui_widgets::popover::Popover` (`popover.rs`). It is a real, shipped, edge-avoidance auto-placement system: give it a list of candidate `PopoverPlacement`s (side + alignment + gap) relative to a parent entity, and its `PostUpdate` system picks whichever candidate keeps the popover fully inside the window rect (minus a configurable `window_margin`), falling back to "least occluded" if none fit cleanly. **[synth-verified, vendored source, `bevy_ui_widgets-0.18.1/src/popover.rs:1-150`]** This is directly useful for a **toast or sticky-banner** that must never clip off-screen, and it's a genuinely different tool than `bevy_ui_anchor` (§6): `Popover` positions relative to a *UI parent entity* inside the same layout tree with edge-avoidance baked in; `bevy_ui_anchor` positions relative to a *world-space point* via camera projection with no edge-avoidance. The two solve adjacent but distinct halves of the panel's stated needs (toast placement vs. globe-point anchoring) and could plausibly both be adopted, at different feature-gate cost (`Popover` needs the `experimental_bevy_ui_widgets` Cargo feature; `bevy_ui_anchor` is an independent crate, no engine feature-gating).

## 10. Dead ends, stated plainly

- **`iyes_perf_ui` and `bevy_screen_diagnostics`** — both stranded two Bevy releases behind, both effectively abandoned-in-practice (not archived, just no activity), neither addresses the chip/alarm/banner/toast shape of this panel even setting version aside. The scope angle that went looking for "a maintained debug-overlay crate to build on" came back empty; nothing here shortens the build.
- **`bevy_mod_billboard`** — over two years stale, pre-rework Bundle API, would need a ground-up rewrite to reach 0.18 even before asking whether it does what's wanted. Its own outline-effect issue (open, unanswered) shows it wouldn't have closed the outline gap anyway.
- **Real glyph-edge text outline** — still genuinely unavailable first-party as of 0.18 (§5), though a PR is in flight (`#23369`) rather than the topic being untouched.
- **Subpixel/LCD text antialiasing** — not a gap that's being worked on or planned around in anything this harvest surfaced; the API surface (`FontSmoothing`) has exactly two variants and nothing in the sourced material suggests a third is coming.
- **A unified "the text changed" change-detection query** — issue #15805, filed by Bevy's own lead maintainer, open since Oct 2024, one comment, no milestone. If the panel's own code needs to react to "did any chip's text change this frame" (as opposed to Bevy's internal layout system reacting to it, which §3 covers), that has to be hand-rolled per component type (`Text`/`Text2d`/`TextSpan`) — there's no first-party helper and none is imminent per this evidence.
- **HiDPI-crisp raster images in `bevy_ui`** — open since 2023-11-14, no milestone, ~2.7 years untouched (§5). Only bites if the panel uses image/sprite icons rather than glyphs for state; text itself is unaffected.

## 11. What I'd flag back on the brief

The brief's guess-list (contrast/backgrounds/shadows/outlines; non-reflow + per-frame cost; pulse-without-timer; world→screen anchoring; screenshot path) turned out to cover the ground well — nothing in the corpus pointed at an important sixth area the guesses missed. The one place the corpus earned its keep beyond the guess-list was narrower and sharper than "a new area": **the per-frame update cost model isn't a performance footnote, it's the direct mechanism of the diagnosed defect** (§3) — the brief characterized the existing HUD's problem as "reflows, changes height frame to frame," which is true, but the vendored-source read shows the *identical* remeasure cost would fire even if the string's on-screen size never visibly changed, purely because `Text` was written to. That reframes the fix from "stop making the box change size" to "stop writing to the block at all except when a value truly changed" — a stricter and more specific target than the brief's framing implied, and I'd treat it as the single highest-leverage sentence in this synthesis.

Nothing in the corpus said "don't use `bevy_ui` for this" or surfaced a total-outsider crate nobody's heard of — the honest report is that stock `bevy_ui`/`bevy_text` genuinely does carry this panel's needs first-party (chrome primitives, DPI, contrast, hinting, smoothing, layout-free transforms), the one real gap is autonomous pulsing (closed by `bevy_easings`, not by anything first-party) and off-screen-arrow math (nobody ships it, it's genuinely 30-60 minutes of `atan2`), and the two most-hyped adjacent options (Feathers, egui) both have real, source-grounded reasons to sit this one out rather than vibes-based ones.
